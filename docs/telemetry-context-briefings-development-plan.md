# Communications Service — telemetry, context integration and briefings
Date: 2026-11-26 | Status: proposed implementation plan | Baseline: main, v2.8.2; merge d08ca2b53127a9ef4d0ea8c4239c87cdde030338 (PR #23)

## Objective and constraints
Make voice conversations measurably responsive, context-aware and useful across calls, without rewriting HyperFlow or Project Flow. Instrument Communications Service first; treat external providers as black boxes (request/response boundaries, elapsed time, sizes and outcomes). Preserve existing caller/line recognition, tenant isolation, tool permissions, privacy and confirmation flows. Do not block greetings on optional context. No external-provider changes are assumed or authorized by this plan.

## Existing baseline and open questions
Main contains line-specific Twilio call/SMS history (PR #23), briefing task creation and explicit section retrieval (October 28 commits). package.json exposes isolated, unit, DB and live tests. index.js integrates phoneLines, realtimeSessions, voiceTurns, hyperflowVoice, briefingVoice, briefingTurnEvidence, toolAudit and Twilio health. Existing briefing tests cover verification, played readback, interrupted tools, privacy and tenant isolation. Reuse these facilities; inventory existing telemetry before adding new instrumentation. Production deployment and real-call latency have not been verified. Existing plan documents could not be retrieved via code search; reconcile with any overlapping docs before implementation. No HyperFlow/Project Flow API coverage claim is made yet.

## Phase 1 — telemetry first (priority)
- [ ] Introduce one trace per communication, child spans for turn, model response, tool and external requests; propagate correlation IDs where supported. Instrument index.js, realtimeSessions.js, voiceTurns.js, tools.js, hyperflowVoice.js, briefingVoice.js and existing context paths. Reuse existing audit/health facilities where appropriate.
- [ ] Record call arrival, identity resolution, history/context load, model connection and session readiness, greeting request/first audio, caller speech end/turn commit, model request/first audio, outbound audio and Twilio playback mark, response completion, interruption, tool dispatch/completion, and call end. Distinguish actual observed playback acknowledgement from first emitted audio; label unavailable timing rather than infer it.
- [ ] Wrap every HyperFlow/Project Flow HTTP call (including retries, background refresh and errors): request start, headers/first byte where available, body read/end, elapsed ms, request/response body bytes (define wire vs decoded), provider, normalized operation, status, timeout, retry count, cache outcome and trace IDs. Do not require provider-side code changes. Record unmeasured fields as null, distinguish an HTTP success from semantic success.
- [ ] Proposed structured event contract: schema_version, trace_id, span_id, parent_span_id, communication_id, tenant_id (access restricted), turn_id, provider, operation, stage, started_at_utc, finished_at_utc, duration_ms (monotonic), request_bytes, response_bytes, outcome, status_code, attempt, cache_status, error_class, build, channel. No raw phone numbers, tokens, verification codes, URLs with secrets, tool arguments/results, message bodies or audio. Use bounded-cardinality aggregate labels; keep IDs in restricted traces only.
- [ ] Export asynchronously with bounded queues, batching, sampling controls and drop counts; failure must never prevent speech. Add authenticated trace inspection by call/turn, latency waterfall, per-provider and operation p50/p95/p99, error/timeout rate, payload distribution, cache hits and slowest stages. Apply tenant-scoped access and configurable retention; proposed 30 days for detailed traces, review before production.
- [ ] Test fake-clock duration and byte accounting, missing events, cancellation, retries, overlapping calls, redaction, tenant isolation and exporter failure. Run a representative baseline with optional integrations disabled then enabled. Proposed initial evaluation: at least 30 scripted turns per scenario; report sample counts and avoid treating sparse p99 as reliable. Measure instrumentation overhead; provisional target under 50 ms p95 on the critical path, revise after baseline.
Gate: traceable representative calls, complete request boundaries, measured critical path and baseline report. Do not enable new synchronous context providers before this gate.

## Phase 2 — HyperFlow and Project Flow API capability audit
- [ ] Identify authoritative deployed API versions, OpenAPI/schema docs, authentication, identity/tenant mapping, pagination, incremental cursors, evidence links, rate limits, request limits, idempotency, permissions, errors and freshness semantics. Inspect actual endpoints and test read-only fixtures using least-privilege credentials. Never equate a repo endpoint with a deployed endpoint without verification.
- [ ] Create coverage matrix (user intent | provider | endpoint/method | request/response schema | auth | scope | freshness | typical/p95 latency and bytes | pagination | status | gap | workaround). Mark each capability verified, partial, missing or untested.
- [ ] HyperFlow: contact/project/thread briefing, promises owed by/to user, due/overdue commitments, decisions, events, recent communications/artifact evidence, changes since a cursor/time, ambiguous identity resolution and supporting evidence. Review existing briefing start/verification, list sections, proposal/confirmation and result operations in briefingVoice.js. Evaluate compact summaries, batch queries and incremental updates before requesting new upstream endpoints.
- [ ] Project Flow: assigned/outstanding/overdue tasks, dependencies, project status/milestones, upcoming deadlines, changes since last check-in, evidence/deep links, and authorized task creation/update where supported. Determine overlap and system of record per entity. Include existing calendar access/operational review where useful.
- [ ] Benchmark cold/warm and small/large queries, using Phase 1 traces. Avoid repeated long queries on a call; document any missing efficient delta/summary operation and alternative. Escalate only proven blocking gaps; provider changes require separate agreement.
Gate: checked-in capability matrix, example sanitized fixtures, latency/size observations, ownership map and gap decisions.

## Phase 3 — controlled context orchestration
- [ ] Extend existing context resolution through a common read adapter; feature flags per provider, tenant, use case and rollout cohort. Distinguish trusted identity/authorization from retrieved content. Scope caches by tenant, user, line, provider, query and access scope; never cache verification secrets or expose private briefings to general memory.
- [ ] Proposed read request: tenant_id, authenticated_subject, service_identity, intent, scope, cursor/as_of, deadline_ms, max_items, max_bytes, trace_id. Result: provider, operation, status (ok/partial/unavailable/forbidden), data, evidence_refs, as_of, fetched_at, next_cursor, truncated, error_class. Normalize with adapters; retain upstream evidence and stable entity IDs. Writes use separate existing permission/confirmation/idempotency paths.
- [ ] Resolve caller/line and minimum existing history first; greet without waiting for optional providers. Run independent authorized reads concurrently; request only intent-relevant bounded results; use short summaries first and fetch evidence on demand. Respect existing voice deadlines and interruptions; late results must not generate stale speech or duplicate actions.
- [ ] Establish configurable per-provider deadlines, circuit breakers, bounded read retries, cancellation, cache freshness and failure fallback. Proposed experimental on-demand read budget 1.5 s (not a measured SLA); tune using Phase 1/2 data. Use an explicit brief spoken progress cue when meaningful, not repeated filler. Show freshness/partial status; never present cached or missing data as current/complete.
- [ ] Validate provider results, guard against instruction injection, preserve existing private briefing verification/readback and line isolation; test same caller across lines, wrong tenant, slow/unavailable provider, contradictory results and interruption.
Gate: provider can be enabled/disabled independently without breaking normal calls, trace comparison demonstrates acceptable latency, and permissions and privacy tests pass.

## Phase 4 — fast daily and incremental briefings
- [ ] Extend the existing briefing flow (do not replace the tested confirmation mechanism). Support daily brief, since last successful check-in, project/contact brief, and on-demand drill-down. Use user timezone for daily window boundaries and UTC for stored cursor/timestamps.
- [ ] Build a compact per-user snapshot with configurable scheduled refresh and incremental provider updates where verified; refresh outside the voice turn, coalesce concurrent refreshes, and allow on-demand refresh when justified. Start with a proposed 15-minute refresh interval during business hours plus a configurable morning refresh; tune to rate limits and observed freshness needs. Do not invent upstream push/delta support; use bounded polling if needed.
- [ ] Snapshot schema: tenant_id, subject_id, scope, briefing_id, generated_at, period_start/end, per-source as_of/status/cursor, sections, item IDs/evidence refs, source attribution, change type, priority, due_at, responsible party, completeness and freshness. Deduplicate by source/entity IDs and verified relationships, not similar names alone. Store per-source watermark only after successful retrieval; track presented items/sections separately, advance a successful check-in cursor only for coverage actually delivered, and do not skip unread changes after interruptions or source outages. Reconcile paginated changes with stable ordering and an overlap window.
- [ ] Briefing sections: today's calendar/upcoming events; commitments I owe; commitments owed to me; overdue/missing deliverables; assigned and blocked project tasks; new decisions and material changes; suggested next actions. Prioritize urgent/overdue and changed items; speak a concise top-line summary first, then offer details and evidence. Explicitly distinguish no items from missing source data.
- [ ] Preserve three-stage human review: briefing, questions/clarifications, then instructions/next actions and closeout. Existing verified approvals and task writes must remain authoritative; only report saved after confirmed success. Capture unresolved questions and follow-ups; do not repeat a mutation if a caller interrupts.
- [ ] Test daily rollover, since-last-check-in, empty/partial/stale snapshot, duplicated cross-provider tasks, missed/interrupted briefing, verification, concurrent refresh and provider outage. Measure snapshot build cost separately from call-time lookup and compare live fan-out against snapshot-first. Proposed target: warm snapshot read under 300 ms p95, subject to baseline calibration.
Gate: representative daily and incremental briefings deliver correct, attributable, fresh-enough content with lower call-time latency than equivalent live lookups; no missed changes or privacy regression.

## Phase 5 — validation, rollout and operational review
- [ ] Run package test suites (npm test, npm run test:unit, npm run test:db; controlled live checks only with authorized test accounts). Add provider contract mocks, deterministic replay, multi-tenant security tests, slow network and provider outage tests. Update schema/docs and test scripts/build fingerprint source list if new modules are introduced.
- [ ] Compare A: existing service; B: telemetry only; C: HyperFlow; D: Project Flow; E: both providers; F: snapshot-first briefing. Same scripted scenarios, call model/config and sample counts; capture caller speech-end to first audible proxy, greetings, tool waits, correctness, payload size, timeout rate and cache freshness. Report p50/p95/p99 where samples permit, with distributions, errors and cost/usage if available.
- [ ] Proposed initial rollout guardrails: no cross-tenant leakage, no duplicate/unauthorized writes, no material regression in ordinary call p95; flag any regression over 10% or 200 ms (whichever is smaller) for review, not an established SLA. Track context availability and briefing correctness alongside speed.
- [ ] Deploy telemetry first, then individually flag read providers, then snapshot briefings; start with test tenants, validate actual production build, widen only after gates pass. Keep rollback flags, backward-compatible migrations, trace export disable switch and documented recovery. No destructive schema changes.
- [ ] Record actual results and remaining issues in repo, with evidence and commit/PR references; update the plan checkboxes as each gate is demonstrated.

## Deliverables and decisions
1. Instrumentation schema, trace viewer/metrics, baseline report and operational runbook.
2. Verified provider API coverage matrix and gap register.
3. Context adapter contracts, flags, timeout/cache policy and tests.
4. Snapshot/delta briefing service, voice integration and correctness fixtures.
5. Comparative performance and release report.

Implementation order is deliberate: baseline and telemetry, then provider audit, then integrations and snapshot briefings. Numeric budgets, refresh interval and retention are proposed engineering defaults, not user-approved or measured service levels. Choose actual storage/export technology after examining existing infrastructure; avoid creating a second telemetry stack unnecessarily. No application code, migrations, production configuration or upstream repositories are changed by this document.
