# Live HyperFlow briefing tools

Coaching and daily briefing calls receive `hyperflow_briefing` when HyperFlow integration is configured and the call has a trusted contact identity. Authorised primary-caller inbound routing also retains it across project selection. HyperFlow's enrolment, SMS verification and capability checks determine access; advertising a tool does not grant it authority.

The tool calls the signed HyperFlow `/api/agent/briefing` endpoint using the existing HyperFlow origin and Communications webhook secret. Model arguments cannot select the tenant, caller, thread, communication, service identity, endpoint or confirmation evidence. No arbitrary HTTP or code-execution tool is exposed.

The conversation requests a verification code, verifies it, then reads current tasks, approvals and reports. Reports support a selected user or all users permitted by HyperFlow. Lists expose pagination and incomplete-source notices. New voice decisions use one caller instruction on the current exact-version item and a saved result. On timeout, query the existing operation result; never repeat an uncertain effect.

Briefing mode uses the `briefing-first.v4` opening. Call `start_briefing` immediately; HyperFlow applies its saved Security option and returns ready or code_sent. Ready means begin the briefing directly, with no SMS or extra identity question. SMS remains the default and is mandatory for inbound calls. Health and call metadata record the prompt version. Before dispatch, the approved prompt/tools and trusted identity are frozen in the outbound receipt and restored at answer/media handoff.

The call assistant interprets natural instructions and uses `decide_item` immediately, fetching details as needed. No phrase whitelist, second approval, transcript wait or focus/timing marker is required. HyperFlow checks the identified record, version, allowed action and existing access, then saves and returns a receipt. The coach briefly acknowledges the saved result and presents the next item. Use change_result after an uncertain result rather than replaying a mutation. Legacy confirm_change retains its old evidence requirements but is no longer advertised to new calls.

Notes are optional: include details supplied by the caller without demanding a separate explanation. Partial completion remains progress rather than overall completion. ASR is optional audit context; it cannot block a new decision. An explicit refusal, question, silence or source text must never be interpreted as an update request.

Input transcription and assistant output events supply trusted turn evidence. New decisions use the fresh committed caller turn and server-pinned current item. Twilio playback marks additionally protect legacy readback confirmations. Verification codes are redacted from tool audit arguments and verification SMS history. Briefing-capable calls are marked private to general conversation memory, including after outcome classification, because their contents can span projects and users. Authorised call records and HyperFlow post-call extraction remain available.

Health advertises `liveBriefing` and `briefingProtocol: briefing-tool.v1`. The runtime fingerprint includes the briefing and audit modules. HyperFlow enrolment defaults off and must be configured before a live acceptance call. No new database migration or provider credential is introduced.

Confirmation evidence is bound to the caller turn that answered a fully played assistant item. A later acknowledgement such as "I am saving that now" cannot replace that readback. Audio completion, per-item playback marks and committed input item IDs remain authoritative when transcripts arrive late or out of order. Interrupted readbacks require a new full readback and fresh confirmation. Readback validation failures return `confirmation_rejected` with result-reconciliation instructions; transport failures remain uncertain. Tool audits retain timing and item identifiers without copying verification codes.

Verification covers trusted request signing, argument stripping, purpose-specific tool exposure, inbound retention and secret redaction. Full live acceptance also requires matching deployed HyperFlow routes/rules, enrolment, a verified caller, real tool results, confirmed source changes and post-call processing. Repository tests alone do not prove that acceptance.
